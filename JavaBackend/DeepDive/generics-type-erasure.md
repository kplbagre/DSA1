# ☕ Generics + Type Erasure — Deep Dive

> After this note you can explain why you can't do `new T()` inside a generic class, what the compiler does with your `List<String>` at compile time vs what the JVM sees at runtime, and why `List<String>` and `List<Integer>` are the same class at runtime.

---

## 🎯 The Problem This Solves

Before Java 5, collections had no type information. You stored an `Object`, you got back an `Object`, and you cast it manually — hoping you remembered what you put in. One wrong cast, and you got a `ClassCastException` at runtime, sometimes in production, sometimes weeks after the bad insert.

```java
// Pre-Java-5: everything is Object
List names = new ArrayList();
names.add("Alice");
names.add(42);   // no compiler error — List accepts any Object
String name = (String) names.get(1);   // ClassCastException at RUNTIME — 42 is not a String
```

Generics solved this by moving the type check from runtime to compile time. You declare `List<String>`, and the compiler rejects `names.add(42)` before the code ever runs. But the way Java implemented generics — through type erasure — introduced a unique set of limitations and surprising behaviors that every senior Java developer needs to understand.

## 📖 Terminology

| Term | Definition |
|---|---|
| **Generic type** | A class or interface with one or more type parameters. `List<E>` is a generic type where `E` is the type parameter. |
| **Type parameter** | A placeholder for a concrete type, declared in angle brackets. `E` in `List<E>`, `K` and `V` in `Map<K, V>`. Convention: `E` (element), `T` (type), `K` (key), `V` (value), `R` (return), `N` (number). |
| **Type argument** | The concrete type substituted for a type parameter. `String` in `List<String>`. |
| **Parameterized type** | A generic type with its type arguments specified. `List<String>` is a parameterized type. |
| **Raw type** | A generic type used without type arguments. `List` instead of `List<String>`. Legal for backward compatibility but defeats the purpose of generics — the compiler can't check types. |
| **Type erasure** | The process by which the compiler removes all generic type information after type-checking. At runtime, `List<String>` is just `List`. The JVM has no knowledge of the type argument. |
| **Bounded type parameter** | A type parameter with constraints. `<T extends Comparable<T>>` means T must implement Comparable. `extends` is used for both classes and interfaces in generics (not `implements`). |
| **Wildcard (`?`)** | A placeholder for an unknown type. `List<?>` means "a list of something, but I don't know what." Used when the specific type doesn't matter to the method. |
| **Upper-bounded wildcard** | `<? extends Number>` — accepts Number or any subclass (Integer, Double, etc.). You can READ from it (get Number) but can't WRITE to it (compiler doesn't know the specific subclass). |
| **Lower-bounded wildcard** | `<? super Integer>` — accepts Integer or any superclass (Number, Object). You can WRITE to it (put Integer) but reads give you Object (compiler only knows the lower bound). |
| **PECS** | Producer Extends, Consumer Super — the mnemonic for choosing wildcard bounds. If the collection PRODUCES values (you read from it), use `extends`. If it CONSUMES values (you write to it), use `super`. |
| **Bridge method** | A synthetic method generated by the compiler to maintain polymorphism after type erasure. When a generic method is overridden with a specific type, the compiler generates a bridge method with the erased signature that delegates to the specific method. |
| **Reifiable type** | A type whose full type information is available at runtime. Primitives, raw types, unparameterized types, and `List<?>` are reifiable. `List<String>` is NOT reifiable — its type argument is erased. |

## 🧠 Mental Model

Think of generics as a **contract enforced by a very strict editor** (the compiler) who then tears up the contract before sending the manuscript to the printer (the JVM). The editor catches every type error in the manuscript — you can't put an Integer where a String belongs. But once the manuscript goes to print, all the type annotations are stripped. The printed book (the bytecode) has plain Object everywhere. The reader (the JVM) never knows there were type constraints.

This is why you can't do `new T()` — at runtime, the JVM doesn't know what `T` is. It's been erased to `Object`. It's why `List<String>` and `List<Integer>` are the same class (`ArrayList`) at runtime — the JVM sees no difference. And it's why you can't check `obj instanceof List<String>` — there's no `String` type information left to check against.

> If you can say "generics are a compile-time type-checking mechanism; the JVM never sees type arguments because they're erased to their bounds (usually Object); this is why you can't instantiate T, create generic arrays, or do instanceof on parameterized types" without notes, you have generics.

## 🎨 Visual — Type Erasure: What the Compiler Does

```
  WHAT YOU WRITE (source code):

  public class Box<T> {
      private T item;
      public void set(T item) { this.item = item; }
      public T get() { return item; }
  }

  Box<String> box = new Box<>();
  box.set("hello");
  String s = box.get();

  ─────────────────────────────────────────────────────
  WHAT THE COMPILER PRODUCES (after type erasure):

  public class Box {              // <T> is gone
      private Object item;        // T → Object
      public void set(Object item) { this.item = item; }
      public Object get() { return item; }
  }

  Box box = new Box();            // no type argument
  box.set("hello");               // still works — String IS an Object
  String s = (String) box.get();  // compiler INSERTS this cast for you

  ─────────────────────────────────────────────────────
  THE CAST IS INVISIBLE IN YOUR SOURCE CODE.
  The compiler verified it's safe at compile time, then inserted it
  into the bytecode. If you never use raw types or unchecked casts,
  the inserted cast will NEVER fail.

KEY INVARIANT:
   Generics = compile-time checking + automatic casting.
   At runtime, all type arguments are erased.
   The JVM runs the same bytecode for Box<String> and Box<Integer>.
```

## 🪜 Build-up

---

### Level 1 — The naive approach (and why it fails)

Before generics, you wrote "general-purpose" code by accepting `Object`:

```java
// Tier 1 — Demo: pre-generics pattern (Java 1.4 style)
public class ObjectBox {
    private Object item;

    public void set(Object item) {
        this.item = item;
    }

    public Object get() {
        return item;
    }
}

ObjectBox box = new ObjectBox();
box.set("hello");
String s = (String) box.get();   // manual cast — works

box.set(42);   // no compiler error — 42 is autoboxed to Integer, which IS an Object
String s2 = (String) box.get();   // ClassCastException at RUNTIME
// Integer cannot be cast to String
// ⚠️ NOT thread-safe — shared mutable state
```

Three problems:
1. **No compile-time safety** — the compiler can't know what type is in the box.
2. **Manual casting everywhere** — verbose and error-prone.
3. **Runtime failures** — ClassCastException discovered in production, not at compile time.

Generics solve all three: `Box<String>` tells the compiler "this box holds Strings", the compiler rejects `box.set(42)`, and the cast is inserted automatically.

### Level 2 — The real mechanism

#### 2.1 — Generic classes and methods

```java
// Tier 1 — Demo: generic class
public class Box<T> {
    private T item;

    public void set(T item) {
        this.item = item;
    }

    public T get() {
        return item;
    }
}

Box<String> stringBox = new Box<>();   // diamond operator (Java 7+)
stringBox.set("hello");
String s = stringBox.get();   // no cast needed — compiler knows it's String
// stringBox.set(42);   // COMPILE ERROR: Integer cannot be converted to String
// ⚠️ NOT thread-safe — same Box instance shared across threads needs synchronization
```

```java
// Tier 1 — Demo: generic method (type parameter on the method, not the class)
public static <T> T firstNonNull(T first, T second) {
    return first != null ? first : second;
}

String result = firstNonNull(null, "default");   // T inferred as String
Integer num = firstNonNull(null, 42);            // T inferred as Integer
```

#### 2.2 — Bounded type parameters

When you need to constrain what T can be:

```java
// Tier 1 — Demo: upper-bounded type parameter
public static <T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}

max(3, 7);           // works — Integer implements Comparable<Integer>
max("cat", "dog");   // works — String implements Comparable<String>
// max(new Object(), new Object());   // COMPILE ERROR — Object doesn't implement Comparable
```

**After type erasure:**

```java
// What the compiler produces:
public static Comparable max(Comparable a, Comparable b) {
    return a.compareTo(b) >= 0 ? a : b;
}
// T is erased to its BOUND (Comparable), not to Object.
// This is why bounded types exist in the bytecode as their bound type.
```

> **What the JVM is actually doing:** When T has a bound (`T extends Comparable<T>`), erasure replaces T with `Comparable`, not `Object`. The bytecode has `Comparable` in all the method signatures. When T has multiple bounds (`T extends Comparable<T> & Serializable`), erasure uses the FIRST bound (`Comparable`) as the erasure type and generates bridge methods for the others. This is why the order of bounds matters — put the class first, interfaces after.

#### 2.3 — Wildcards and PECS

**The problem wildcards solve:**

```java
// Without wildcards — this is too restrictive:
public static double sum(List<Number> numbers) {
    double total = 0;
    for (Number n : numbers) {
        total += n.doubleValue();
    }
    return total;
}

List<Integer> ints = List.of(1, 2, 3);
// sum(ints);   // COMPILE ERROR — List<Integer> is NOT a subtype of List<Number>
// Even though Integer IS a subtype of Number, generic types are INVARIANT
```

**Why `List<Integer>` is NOT a subtype of `List<Number>`:**

```
  If it were, you could do this:
  List<Integer> ints = new ArrayList<>();
  List<Number> nums = ints;   // hypothetically legal
  nums.add(3.14);             // legal — Double IS a Number
  Integer i = ints.get(0);    // ClassCastException — it's actually a Double!

  Generic types are INVARIANT to prevent this heap pollution.
  Arrays are COVARIANT (Integer[] IS a Number[]) — and this exact bug
  happens with arrays (ArrayStoreException at runtime). Generics
  fixed this by being invariant at compile time.
```

**Upper-bounded wildcard — `extends` (PRODUCER):**

```java
// "I will READ from this collection, not WRITE to it"
public static double sum(List<? extends Number> numbers) {
    double total = 0;
    for (Number n : numbers) {   // safe — every element IS at least a Number
        total += n.doubleValue();
    }
    // numbers.add(42);   // COMPILE ERROR — compiler doesn't know the specific subtype
    return total;
}

sum(List.of(1, 2, 3));          // works — List<Integer>
sum(List.of(1.5, 2.5));         // works — List<Double>
```

**Lower-bounded wildcard — `super` (CONSUMER):**

```java
// "I will WRITE to this collection, not care about the specific read type"
public static void addIntegers(List<? super Integer> target) {
    target.add(1);    // safe — the list accepts at least Integer
    target.add(2);
    // Integer i = target.get(0);   // COMPILE ERROR — get() returns Object
    //                               // (compiler only knows the lower bound)
}

List<Number> nums = new ArrayList<>();
addIntegers(nums);     // works — Number IS a supertype of Integer
List<Object> objs = new ArrayList<>();
addIntegers(objs);     // works — Object IS a supertype of Integer
```

**PECS — the mnemonic:**

```
  PECS = Producer Extends, Consumer Super

  If the collection PRODUCES values for you (you READ from it):
    → use <? extends T>  (you know each element is at least T)

  If the collection CONSUMES values from you (you WRITE to it):
    → use <? super T>  (you know the collection accepts at least T)

  If you both read and write:
    → use exact type <T>  (no wildcard)

  Example from JDK:
  Collections.copy(List<? super T> dest, List<? extends T> src)
                   ^^^^^^^^^^^^^^         ^^^^^^^^^^^^^^^
                   consumer (write to)    producer (read from)
```

#### 2.4 — Type erasure in detail

At compile time, the compiler:
1. **Type-checks** all generic operations (rejects invalid types).
2. **Erases** all type parameters — replaces them with their bounds (Object if unbounded).
3. **Inserts casts** wherever the erased type (Object) is assigned to a typed variable.
4. **Generates bridge methods** to maintain polymorphism.

```java
// BEFORE ERASURE (your source code):
public class Pair<A, B> {
    private A first;
    private B second;
    public A getFirst() { return first; }
}

Pair<String, Integer> p = new Pair<>();
String s = p.getFirst();

// AFTER ERASURE (what the JVM sees):
public class Pair {
    private Object first;    // A → Object
    private Object second;   // B → Object
    public Object getFirst() { return first; }
}

Pair p = new Pair();
String s = (String) p.getFirst();   // compiler inserted this cast
```

> **What the JVM is actually doing:** At the bytecode level, there is ONE `Pair.class` file — not one per type argument combination. `Pair<String, Integer>` and `Pair<Double, Long>` use the same class, the same method signatures, the same field types. The type argument exists only as metadata in the classfile's `Signature` attribute (readable via reflection's `getGenericSuperclass()` and `getGenericInterfaces()`) — but it's not used by the JVM for any runtime operation. No specialization, no code duplication. This is fundamentally different from C++ templates, which generate separate code for each type argument.

#### 2.5 — Bridge methods

When a generic method is overridden with a specific type, the compiler generates a bridge method to maintain runtime polymorphism:

```java
// Tier 1 — Demo: bridge method generation
public interface Comparable<T> {
    int compareTo(T other);
}

public class Age implements Comparable<Age> {
    private final int years;

    @Override
    public int compareTo(Age other) {   // specific type: Age
        return Integer.compare(years, other.years);
    }
}

// After erasure, Comparable becomes:
// public interface Comparable {
//     int compareTo(Object other);   // T → Object
// }

// Age's method signature is:
//     int compareTo(Age other);      // specific type, NOT Object

// The compiler generates a BRIDGE METHOD to connect them:
// public int compareTo(Object other) {    // ← bridge (synthetic)
//     return compareTo((Age) other);      // delegates to the real method
// }
```

You can see bridge methods via reflection: `method.isBridge()` returns true. They show up in stack traces sometimes, which confuses developers who don't know about erasure.

### Level 3 — The subtleties

#### 3.1 — What you CAN'T do with generics (and why)

Every limitation traces back to type erasure — at runtime, T doesn't exist.

```java
public class GenericBox<T> {
    // ❌ Can't instantiate T — JVM doesn't know what T is
    // T item = new T();   // COMPILE ERROR

    // ❌ Can't create generic array — arrays carry runtime type info, generics don't
    // T[] items = new T[10];   // COMPILE ERROR

    // ❌ Can't use instanceof with parameterized type — type argument erased
    // if (obj instanceof List<String>) {}   // COMPILE ERROR
    // ✅ Can use instanceof with unbounded wildcard:
    // if (obj instanceof List<?>) {}        // OK — no type argument to check

    // ❌ Can't use T in static context — T belongs to the instance, not the class
    // private static T staticField;   // COMPILE ERROR

    // ❌ Can't catch or throw generic type — JVM exception handling needs exact types
    // catch (T e) {}   // COMPILE ERROR
}
```

**Workaround for instantiation — pass the Class:**

```java
// Tier 2 — Production: creating T instances via Class token
public class Factory<T> {
    private final Class<T> type;

    public Factory(Class<T> type) {
        this.type = type;
    }

    public T create() throws ReflectiveOperationException {
        return type.getDeclaredConstructor().newInstance();
    }
}

Factory<StringBuilder> factory = new Factory<>(StringBuilder.class);
StringBuilder sb = factory.create();   // works — Class token carries runtime type info
```

#### 3.2 — Generic array creation problem

```java
// ❌ This is illegal:
List<String>[] stringLists = new List<String>[10];

// WHY? If it were legal:
Object[] objects = stringLists;         // array covariance allows this
objects[0] = List.of(42);              // List<Integer> stored — no ArrayStoreException
//                                      because at runtime, List<String> and List<Integer>
//                                      are both just List
String s = stringLists[0].get(0);      // ClassCastException — it's an Integer
// Generics exist to PREVENT ClassCastException. Allowing generic arrays would undermine them.

// ✅ Workaround: use List<List<String>> instead
List<List<String>> listOfLists = new ArrayList<>();
```

#### 3.3 — Raw types and unchecked warnings

```java
// Tier 1 — Demo: raw type usage (legal but dangerous)
List rawList = new ArrayList();   // raw type — no type argument
rawList.add("hello");
rawList.add(42);   // no compiler error — raw type bypasses generics

List<String> typedList = rawList;   // unchecked assignment — WARNING, not error
// javac: warning: unchecked or unsafe operations
// The compiler can no longer guarantee type safety for typedList.
String s = typedList.get(1);   // ClassCastException at runtime — 42 is not String
```

**Rule:** raw types exist ONLY for backward compatibility with pre-Java-5 code. Never use them in new code. If you see `@SuppressWarnings("unchecked")`, it means someone is bypassing the generic type system — review it carefully.

#### 3.4 — Type information available at runtime via reflection

Even though type arguments are erased from method bodies, they're preserved as metadata in class signatures:

```java
// Tier 1 — Demo: recovering type info from class hierarchy
public class StringList extends ArrayList<String> {}

// At runtime:
Type superclass = StringList.class.getGenericSuperclass();
// superclass = ArrayList<String>  ← type argument IS available!

ParameterizedType pt = (ParameterizedType) superclass;
Type[] typeArgs = pt.getActualTypeArguments();
System.out.println(typeArgs[0]);   // class java.lang.String
```

**This is how frameworks work:** Spring, Jackson, Gson, and TypeReference in Jackson all use this trick. When you write `new TypeReference<List<String>>() {}`, the anonymous class extends `TypeReference<List<String>>` — the type argument is baked into the class hierarchy and survives erasure.

```java
// Tier 3 — Framework: Jackson TypeReference pattern
ObjectMapper mapper = new ObjectMapper();
List<User> users = mapper.readValue(json, new TypeReference<List<User>>() {});
// The anonymous class preserves List<User> in its generic superclass signature
// Jackson reads it via getGenericSuperclass() at runtime
```

## ⚠️ Common Misconceptions

| You might think... | But actually... |
|---|---|
| "`List<String>` and `List<Integer>` are different classes at runtime" | They are the SAME class (`ArrayList`). Type arguments are erased. `new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()` is true. |
| "Generics make code slower because of the casting" | The casts inserted by the compiler are the same casts you'd write manually without generics. No performance difference. Generics are a zero-cost abstraction at runtime (unlike C++ templates, which can cause code bloat). |
| "`T extends Comparable` means T must be a subclass of Comparable" | In generics, `extends` is used for both classes AND interfaces. `T extends Comparable` means T implements Comparable. There is no `T implements Comparable` syntax in generic bounds. |
| "Wildcards and type parameters are interchangeable" | Type parameters (`<T>`) name the type so you can reference it multiple times (e.g., `T get()` and `void set(T item)`). Wildcards (`<?>`) are unnamed — you can't reference the type elsewhere. Use type parameters when you need the type in multiple places; wildcards when you need it in exactly one place. |
| "I can check `obj instanceof List<String>` at runtime" | You can't — `List<String>` is not reifiable (its type argument is erased). You can check `obj instanceof List<?>` (unbounded wildcard is reifiable) but not `List<String>`. This is why generic type checks require passing a `Class<T>` token. |

## 🐞 Production Footguns

---

> **Footgun: Heap pollution via raw types**
> **Cost:** ClassCastException in production
>
> In a legacy data pipeline, a utility method accepted a raw `List` and added mixed types. Downstream code assigned the result to a `List<String>` — no compiler error (just a warning). The ClassCastException occurred hundreds of lines later, in a completely different module, when the list was iterated and a non-String element was cast — making the bug nearly impossible to trace to its source.

```java
// ❌ The trap: raw type method pollutes typed callers
public static void addDefaults(List list) {   // raw type
    list.add("default");
    list.add(42);   // no error — raw type skips generic checks
}

List<String> names = new ArrayList<>();
addDefaults(names);   // unchecked warning — ignored
// names now contains: ["default", 42]
String first = names.get(0);   // works
String second = names.get(1);  // ClassCastException — 42 is not String
// The exception points HERE, not at addDefaults() — misleading stack trace

// ✅ The fix: use generics in the method signature
public static void addDefaults(List<String> list) {
    list.add("default");
    // list.add(42);   // COMPILE ERROR — caught at the source
}
// ⚠️ NOT thread-safe — pass a synchronized or concurrent list if shared
```

---

> **Footgun: Unchecked cast hiding type mismatch**
> **Cost:** Silent data corruption
>
> In a Spring configuration service, a generic cache method used `@SuppressWarnings("unchecked")` to cast the return type. The cache stored `Object` values but the method signature promised `T`. A developer stored a `List<Integer>` under a key but retrieved it as `List<String>`. The cast to `List` succeeded (erasure — both are just `List`) and no exception was thrown. The `ClassCastException` occurred much later when a `String` method was called on an `Integer` element — in a different service that consumed the data.

```java
// ❌ The trap: @SuppressWarnings("unchecked") hides type mismatch
@SuppressWarnings("unchecked")
public <T> T getFromCache(String key) {
    return (T) cache.get(key);   // unchecked cast — compiler trusts you
}

// Stored as List<Integer>:
cache.put("data", List.of(1, 2, 3));

// Retrieved as List<String> — NO ClassCastException here:
List<String> data = getFromCache("data");
// At runtime: (List) cache.get("data") → List — cast succeeds (erasure)

// CCE happens HERE, far from the real bug:
String first = data.get(0);   // ClassCastException: Integer cannot be cast to String

// ✅ The fix: use Class token for type-safe cast
public <T> T getFromCache(String key, Class<T> type) {
    Object value = cache.get(key);
    return type.cast(value);   // throws ClassCastException at the POINT OF RETRIEVAL
}
// Now the error occurs where the type mismatch is, not downstream
```

## 🎙️ Interview Deep Questions

**Q1. What is type erasure and why did Java choose it over reification (like C# or C++ templates)?**

> Type erasure means the compiler removes all generic type information after type-checking. At runtime, `List<String>` is just `List` and `T` is just `Object` (or its bound). Java chose erasure for backward compatibility — when generics were added in Java 5, billions of lines of pre-generics code and millions of compiled `.class` files existed. Erasure ensured that `List<String>` and raw `List` produce the same bytecode, so old and new code could interoperate without recompiling the entire Java ecosystem. C# was designed with generics from the start (added in C# 2.0, but the CLR was redesigned to support them natively), so it could afford reification — type information at runtime. The trade-off: Java gets perfect backward compatibility but loses runtime type information; C# gets runtime type info but required a VM redesign.

**Q2. What is PECS? Give me a real example from the JDK.**

> PECS stands for Producer Extends, Consumer Super. If a collection produces values for you (you read from it), declare it with `<? extends T>` — you know each element is at least T. If a collection consumes values from you (you write to it), declare it with `<? super T>` — the collection accepts at least T. The canonical JDK example is `Collections.copy(List<? super T> dest, List<? extends T> src)`: the source is a producer (you read from it, so `extends`), the destination is a consumer (you write to it, so `super`). Another example: `Stream.map(Function<? super T, ? extends R>)` — T is consumed by the function (input, so `super`), R is produced by the function (output, so `extends`).

**Q3. Why can't you create a generic array like `new T[10]` or `new List<String>[10]`?**

> Arrays in Java carry their component type at runtime (they are reifiable) and enforce it via `ArrayStoreException`. `String[]` knows it's a String array and throws if you store an Integer. But generic types are erased — `List<String>` and `List<Integer>` are both just `List` at runtime. If you could create `List<String>[]`, array covariance would let you assign it to `Object[]`, then store a `List<Integer>` in it — no `ArrayStoreException` because both are just `List` at runtime. Later, reading `List<String>` from the array and calling `get()` would produce a `ClassCastException` from the compiler-inserted cast. Java prevents this at the source by making generic array creation a compile error. The workaround is `List<List<String>>` instead of `List<String>[]`.

**Q4. How do frameworks like Jackson recover generic type information at runtime if it's erased?**

> Type arguments are erased from method bodies and local variables, but they're preserved in class signatures — specifically in the `Signature` attribute of the classfile, accessible via `Class.getGenericSuperclass()` and `Class.getGenericInterfaces()`. When you write `new TypeReference<List<User>>() {}`, the anonymous class extends `TypeReference<List<User>>`. The type argument `List<User>` is baked into the class hierarchy at compile time and survives erasure. At runtime, Jackson calls `getGenericSuperclass()` on the anonymous class, gets `TypeReference<List<User>>`, extracts the `ParameterizedType`, and recovers `List<User>` — including the `User` argument. This is the "super type token" pattern, first described by Neal Gafter.

**Q5. What is invariance in generics? Why is `List<Integer>` NOT a subtype of `List<Number>` even though `Integer` IS a subtype of `Number`?**

> Generic types are invariant: `List<Integer>` is NOT a subtype of `List<Number>`, even though `Integer extends Number`. This is deliberate — if `List<Integer>` were a subtype of `List<Number>`, you could assign a `List<Integer>` to a `List<Number>` variable and then add a `Double` to it (since `Double` is a `Number`). Now the `List<Integer>` contains a `Double` — heap pollution. Java arrays made this mistake: `Integer[]` IS a subtype of `Number[]`, and you CAN store a `Double` in it — you get an `ArrayStoreException` at runtime instead of a compile error. Generics fixed this by being invariant at compile time and using wildcards (`? extends`, `? super`) to express covariance and contravariance explicitly and safely.

## 🎙️ Say It in 60 Seconds

> **Part 1 — What (10s):** Generics are a compile-time type-checking mechanism. They let you write type-safe code that works with any type, without manual casting. At runtime, all type arguments are erased — the JVM never sees them.
>
> **Part 2 — How/Why (30s):** The compiler checks that you use the correct types, then erases all type parameters — replacing T with its bound (usually Object) and inserting casts where needed. This is called type erasure, and Java chose it for backward compatibility with pre-Java-5 code. The consequence: you can't instantiate T, can't create generic arrays, and can't use instanceof on parameterized types — because at runtime, T doesn't exist. Wildcards add flexibility: `? extends T` for reading (producer), `? super T` for writing (consumer) — the PECS rule.
>
> **Part 3 — Gotcha (20s):** The biggest production trap is `@SuppressWarnings("unchecked")` hiding type mismatches. The unchecked cast succeeds at the point of the cast (because both sides are erased to the same raw type), but the ClassCastException occurs far downstream when the wrong type is actually used — making the bug extremely hard to trace. Always use a `Class<T>` token for type-safe casts in generic utility methods.

## 🧾 TL;DR

- Generics = compile-time type checking + automatic casting. Zero-cost at runtime.
- Type erasure: compiler removes all type arguments. JVM sees `Object`, not `T`.
- `List<String>` and `List<Integer>` are the same class at runtime.
- Can't do: `new T()`, `new T[]`, `instanceof List<String>`, `catch (T e)`.
- Bounded types: `<T extends Comparable<T>>` → erased to `Comparable`, not `Object`.
- PECS: Producer Extends, Consumer Super. Read → `? extends`. Write → `? super`.
- Bridge methods preserve polymorphism after erasure — compiler-generated, visible in reflection.
- Frameworks recover type info via `getGenericSuperclass()` on anonymous subclasses (super type token pattern).
