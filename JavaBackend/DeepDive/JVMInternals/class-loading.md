# ⚙️ Class Loading + ClassLoader — Deep Dive

> After this note you can explain the 3 phases of class loading (load → link → initialize), the parent delegation model, why it exists (security + uniqueness), when custom ClassLoaders are needed, and how hot-reloading works in app servers.

---

## 🎯 The Problem This Solves

When you write `new OrderService()`, where does the JVM find `OrderService.class`? How does it know the bytecode is valid? When does the static initializer run? And why can the same class exist twice in memory with different ClassLoaders — and not be `instanceof`-compatible? Class loading is the mechanism that turns `.class` files into usable types at runtime. Understanding it explains classloader-related bugs (`ClassNotFoundException`, `NoClassDefFoundError`, `ClassCastException` between "identical" classes), hot-reloading, and plugin architectures.

---

## 📖 Terminology

| Term | Definition |
|---|---|
| **ClassLoader** | An object responsible for loading class bytecode from a source (filesystem, JAR, network, generated bytes) and defining the `Class<?>` object in the JVM. |
| **Parent delegation model** | When asked to load a class, a ClassLoader first delegates to its parent. The parent delegates to ITS parent. Only if no ancestor can load the class does the original ClassLoader try itself. This ensures core classes (java.lang.String) are always loaded by the bootstrap loader — never overridden. |
| **Bootstrap ClassLoader** | The root loader. Implemented in native code (not a Java object). Loads `java.base` module classes (java.lang.*, java.util.*, etc.) from the JDK's internal modules. |
| **Platform ClassLoader** | (Java 9+, replaces Extension ClassLoader.) Loads platform modules — javax.*, java.sql.*, etc. Parent: Bootstrap. |
| **Application ClassLoader** | Loads classes from the application classpath (-cp, -classpath, module path). The ClassLoader your code uses by default. Parent: Platform. |
| **Linking** | The second phase: Verification (bytecode is valid, no illegal operations), Preparation (allocate memory for static fields, set to default values), Resolution (resolve symbolic references to actual classes/methods). |
| **Initialization** | The third phase: execute static initializers (`static { ... }`) and static field assignments in declaration order. Happens once per class, guaranteed thread-safe by the JVM. |

---

## 🧠 Mental Model

Class loading is a **three-step factory**: Load (find the raw `.class` bytes), Link (verify, prepare memory, resolve references), Initialize (run static blocks). The factory has a **hierarchy of suppliers** (Bootstrap → Platform → Application). When you order a class, the Application ClassLoader asks Platform first, which asks Bootstrap first. If Bootstrap has it (java.lang.String), it's used. If not, it falls back down the chain. This ensures you can never replace `java.lang.String` with a malicious version — Bootstrap always loads it.

> If you can say "3 phases: load (find bytes) → link (verify + prepare + resolve) → initialize (static blocks); parent delegation: child asks parent first → ensures core classes are always loaded by Bootstrap; a class is identified by its fully qualified name + its ClassLoader — same name from different ClassLoaders = different Class objects" without notes, you have class loading.

## 🎨 Visual — Parent Delegation

```
  CLASS LOADING REQUEST: load "com.walmart.OrderService"

  Application ClassLoader:
  "Can I load this? Let me ask my parent first."
       │
       ▼
  Platform ClassLoader:
  "Can I load this? Let me ask MY parent first."
       │
       ▼
  Bootstrap ClassLoader:
  "com.walmart.OrderService? Not in java.base. → NOT FOUND."
       │
       ▼ (returns to Platform)
  Platform ClassLoader:
  "Not in platform modules either. → NOT FOUND."
       │
       ▼ (returns to Application)
  Application ClassLoader:
  "Let me check the classpath... found OrderService.class in app.jar!"
  → loads the bytecode → defines the Class → returns Class<OrderService>

  SECURITY: if someone puts a malicious java.lang.String on the classpath,
  Application ClassLoader asks Platform, Platform asks Bootstrap.
  Bootstrap HAS java.lang.String → loads the real one. Malicious version is NEVER loaded.

KEY INVARIANT:
   Parent delegation ensures: core Java classes are ALWAYS loaded by
   Bootstrap. Application classes can never shadow/replace them.
   A class's identity = fully qualified name + ClassLoader.
   Same name + different ClassLoader = different Class (not instanceof-compatible).
```

// Most developers never think about class loading — until it breaks.

// Two different ClassLoaders loaded the same class → they're different Class objects

// Looks like "OrderService cannot be cast to OrderService" — maddening

### Level 2 — The real mechanism

#### 2.1 — The 3 phases

```
  PHASE 1 — LOADING:
  Find the .class file (filesystem, JAR, network, generated).
  Read the raw bytes into memory.
  Create a Class<?> object in Metaspace.

  PHASE 2 — LINKING (3 sub-steps):
  a) VERIFICATION: check bytecode is structurally valid.
     - Magic number (0xCAFEBABE at the start of every .class file)
     - Valid constant pool entries
     - No illegal operations (e.g., accessing private fields from outside)
     - Stack frames are balanced (no underflow/overflow)
     Verification catches malformed or malicious bytecode BEFORE execution.

  b) PREPARATION: allocate memory for static fields, set to DEFAULT values.
     static int count;   → 0 (not the value you assigned — that's initialization)
     static String name; → null
     No user code runs yet.

  c) RESOLUTION: resolve symbolic references to actual classes/methods.
     "java/lang/String" (symbolic) → Class<String> (resolved)
     May be lazy (resolved on first use) or eager (resolved during linking).

  PHASE 3 — INITIALIZATION:
  Execute static initializers and static field assignments in source order.
  static int count = 42;      → count is set to 42 (was 0 from preparation)
  static { loadConfig(); }    → loadConfig() runs

  ⚠️ Initialization is GUARANTEED thread-safe by the JVM.
  If two threads trigger initialization simultaneously, the JVM ensures
  exactly one thread runs the <clinit> method; the other waits.
  This is why the Holder pattern for singletons is thread-safe:
  class Holder { static final Singleton INSTANCE = new Singleton(); }
  The JVM's class initialization lock ensures INSTANCE is created exactly once.
```

> **What the JVM is actually doing:** The Class object is allocated in Metaspace (native memory, not heap — since Java 8). The bytecode is stored in Metaspace alongside the Class object's metadata (field descriptors, method dispatch table, constant pool). Instance objects live on the heap; their class metadata lives in Metaspace. When Metaspace fills up → `OutOfMemoryError: Metaspace` (the replacement for the old PermGen error).

#### 2.2 — Parent delegation implementation

```java
// Simplified from java.lang.ClassLoader (JDK 21):
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    // 1. Check if already loaded
    Class<?> c = findLoadedClass(name);
    if (c != null) {
        return c;
    }

    // 2. Delegate to parent (recursion up the chain)
    try {
        if (parent != null) {
            c = parent.loadClass(name, false);
        } else {
            c = findBootstrapClassOrNull(name);   // bootstrap is native, not a Java object
        }
    } catch (ClassNotFoundException e) {
        // parent couldn't load → fall through to this ClassLoader
    }

    // 3. If parent didn't find it, try this ClassLoader
    if (c == null) {
        c = findClass(name);   // subclasses override this to find bytes
    }

    return c;
}
```

#### 2.3 — Class identity = name + ClassLoader

```java
// Same class name, different ClassLoaders = different Class objects
ClassLoader cl1 = new URLClassLoader(new URL[]{jarUrl});
ClassLoader cl2 = new URLClassLoader(new URL[]{jarUrl});

Class<?> class1 = cl1.loadClass("com.example.Plugin");
Class<?> class2 = cl2.loadClass("com.example.Plugin");

class1 == class2;   // FALSE — different Class objects
class1.equals(class2);   // FALSE

Object obj = class1.getDeclaredConstructor().newInstance();
class2.isInstance(obj);   // FALSE — not instanceof
class2.cast(obj);         // ClassCastException!
// "Plugin cannot be cast to Plugin" — same name, different ClassLoaders
```

**Where this happens in practice:** application servers (Tomcat, JBoss) give each deployed WAR its own ClassLoader. Two WARs using the same library version have independent Class objects for that library. If one WAR passes an object to the other, ClassCastException — even though the types "look" identical.

### Level 3 — The subtleties

#### 3.1 — Custom ClassLoader (plugin architectures)

```java
// Tier 2 — Production: load a plugin JAR at runtime
public class PluginClassLoader extends URLClassLoader {
    public PluginClassLoader(URL[] urls) {
        super(urls, ClassLoader.getSystemClassLoader());
    }

    // Override to BREAK parent delegation for plugin classes:
    // Load plugin classes from plugin JAR first, THEN delegate to parent
    // This allows plugins to use different versions of shared libraries
    @Override
    protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
        // Always delegate java.* and javax.* to parent (required by spec)
        if (name.startsWith("java.") || name.startsWith("javax.")) {
            return super.loadClass(name, resolve);
        }

        // Try loading from plugin JAR first
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                c = findClass(name);   // load from plugin JAR
            } catch (ClassNotFoundException e) {
                c = super.loadClass(name, resolve);   // fall back to parent
            }
        }
        return c;
    }
}
```

**Use cases for custom ClassLoaders:**
- **Plugin systems:** each plugin gets its own ClassLoader → can use different library versions
- **App servers:** each WAR/EAR gets its own ClassLoader → isolated deployments
- **Hot-reloading:** create a new ClassLoader, reload the class → old ClassLoader (and its classes) become GC-eligible
- **Code generation:** `defineClass(bytes)` — load dynamically generated bytecode (used by Hibernate proxies, Spring CGLIB proxies, Mockito)

#### 3.2 — `Class.forName()` vs `ClassLoader.loadClass()`

```java
// Class.forName("com.example.MyClass"):
// - Uses the CALLER'S ClassLoader
// - Triggers initialization (static blocks run)
// - Commonly used by JDBC: Class.forName("com.mysql.cj.jdbc.Driver")
//   → the Driver's static block registers itself with DriverManager

// ClassLoader.loadClass("com.example.MyClass"):
// - Does NOT trigger initialization by default
// - Only loads + links — initialization deferred until first use
// - Used when you want to load a class without side effects
```

#### 3.3 — `ClassNotFoundException` vs `NoClassDefFoundError`

```java
// ClassNotFoundException (checked exception):
// Class was NEVER found. Thrown by Class.forName() or ClassLoader.loadClass().
// Cause: missing JAR on classpath, typo in class name.

// NoClassDefFoundError (Error — unchecked):
// Class WAS found at compile time but NOT at runtime.
// OR: class was found but its static initializer THREW an exception.
// After a static init failure, the class is marked as unusable forever
// → every subsequent access throws NoClassDefFoundError (not the original exception).
```

## ⚠️ Common Misconceptions

| You might think... | But actually... |
|---|---|
| "There's only one ClassLoader" | There are at least 3 (Bootstrap, Platform, Application), and app servers/plugins add more. Each creates an isolated class namespace. |
| "Same class name = same Class object" | A class is identified by name + ClassLoader. Same name from different ClassLoaders = different, incompatible Class objects. `instanceof` returns false across ClassLoader boundaries. |
| "Static blocks run when the class is loaded" | Static blocks run during INITIALIZATION (phase 3), not loading (phase 1). `ClassLoader.loadClass()` only loads + links — initialization is deferred. `Class.forName()` triggers initialization. |
| "Class loading is done once and forgotten" | Classes can be GC'd when their ClassLoader is GC'd. In app servers, undeploying a WAR makes its ClassLoader eligible for GC → all classes loaded by it become GC-eligible. This is how hot-redeploy works. |

## 🐞 Production Footguns

---

> **Footgun: ClassLoader leak in app server redeploy**
> **Cost:** Metaspace OOM after repeated redeploys
>
> A web application registered a `ThreadLocal`, a JDBC driver, or a shutdown hook during startup. On undeploy, the ClassLoader couldn't be GC'd because these references held strong links to classes loaded by it. After 5-6 redeploys, Metaspace filled up → `OutOfMemoryError: Metaspace`. The only fix was restarting the app server.

```java
// ❌ The trap: strong reference prevents ClassLoader GC
static {
    Runtime.getRuntime().addShutdownHook(new Thread(() -> cleanup()));
    // The shutdown hook holds a reference to the Runnable
    // The Runnable is loaded by the WAR's ClassLoader
    // → ClassLoader can never be GC'd after undeploy
}

// ✅ The fix: clean up in a ServletContextListener
@WebListener
public class AppCleanup implements ServletContextListener {
    @Override
    public void contextDestroyed(ServletContextEvent sce) {
        // Remove shutdown hooks, deregister JDBC drivers,
        // remove ThreadLocals — allow ClassLoader GC
        Enumeration<Driver> drivers = DriverManager.getDrivers();
        while (drivers.hasMoreElements()) {
            Driver driver = drivers.nextElement();
            if (driver.getClass().getClassLoader() == getClass().getClassLoader()) {
                DriverManager.deregisterDriver(driver);
            }
        }
    }
}
```

## 🎙️ Interview Deep Questions

**Q1. What are the 3 phases of class loading?**

> Loading: find the .class bytecode (filesystem, JAR, network) and create a Class object in Metaspace. Linking: three sub-steps — verification (validate bytecode is safe and well-formed), preparation (allocate memory for static fields with default values — 0, null, false), resolution (resolve symbolic references like class names and method signatures to actual Class objects and method pointers). Initialization: execute static initializers and static field assignments in source order. Initialization is guaranteed thread-safe — the JVM holds a lock per class during initialization. This is why the Holder singleton pattern is safe: the JVM ensures `Holder.INSTANCE` is initialized exactly once, even under concurrent access.

**Q2. What is the parent delegation model and why does it exist?**

> When a ClassLoader is asked to load a class, it first delegates to its parent. The parent delegates to its parent. Only if the entire ancestor chain can't load the class does the original ClassLoader try. This exists for two reasons: security — you can't replace `java.lang.String` with a malicious version because Bootstrap always loads it first; and uniqueness — each class is loaded once per ClassLoader chain, preventing duplicate definitions. Breaking parent delegation (loading child-first) is how plugin systems allow different plugins to use different versions of the same library — each plugin's ClassLoader loads its own version before delegating.

**Q3. What is the difference between `ClassNotFoundException` and `NoClassDefFoundError`?**

> `ClassNotFoundException` is a checked exception thrown by `Class.forName()` or `ClassLoader.loadClass()` when the class bytes are not found on any ClassLoader's search path. Fix: add the JAR to the classpath. `NoClassDefFoundError` is an Error thrown when the class was found at compile time but not at runtime, OR when the class's static initializer threw an exception — making the class permanently unusable. After a static init failure, every subsequent access throws `NoClassDefFoundError`, not the original exception — this makes debugging hard because the root cause (the first failure) may have scrolled out of the logs.

**Q4. How does hot-reloading work in application servers?**

> Each deployed WAR/EAR gets its own ClassLoader. The server loads the application's classes using this ClassLoader. On redeploy: the server creates a NEW ClassLoader, loads the updated classes, and discards the old ClassLoader. When no strong references point to the old ClassLoader, it becomes GC-eligible — and all Class objects it loaded are GC'd from Metaspace. This is "hot-reloading." The pitfall: if the old application registered a `ThreadLocal`, shutdown hook, or JDBC driver that holds a reference to a class loaded by the old ClassLoader, the ClassLoader can never be GC'd → Metaspace leak → OOM after multiple redeploys.

## 🧾 TL;DR

- **3 phases:** Load (find bytes) → Link (verify + prepare + resolve) → Initialize (static blocks).
- **Parent delegation:** child asks parent first. Bootstrap always loads java.*. Prevents class spoofing.
- **Class identity = name + ClassLoader.** Same name, different ClassLoader = different Class.
- **Bootstrap** (java.base) → **Platform** (javax) → **Application** (classpath).
- **Initialization is thread-safe** — JVM locks during `<clinit>`. Holder singleton is safe because of this.
- **ClassNotFoundException** = class not found at all. **NoClassDefFoundError** = found at compile time, missing at runtime (or static init failed).
- **Hot-reload** = new ClassLoader → old ClassLoader GC'd → old classes GC'd from Metaspace.
- **ClassLoader leak** = strong reference prevents GC → Metaspace OOM after redeploys.
